# ADR 0002: 로컬 웹의 기술 스택 (PRD Q9)

- **상태**: 제안됨 (Proposed) — 개발 B 검토 후 개발 B·C가 확정
- **작성 일자**: 2026-11-11
- **결정 담당**: 개발 B, 개발 C (PRD 6장)
- **관련 문서**: [PRD 6장·7장 Q9](../PRD.md), [POLICY 1-3, 2-5, 3-4](../POLICY.md), [SPEC 1-4~1-8, 2-5, 3-3~3-5, 5장](../SPEC.md)

## 1. 배경 및 문제 상황

로컬 웹(우주 홈, 행성 패널, 별 상세, 탐사선)을 무엇으로 만들지 정해야 웹 뼈대(이슈 #2)를 시작할 수 있다. 웹 뼈대 위에 개발 A(탐사선)와 개발 B(행성 패널·별 상세)가 화면을 얹으므로, 이 결정이 늦어지면 웹 전체가 늦어진다.

이미 정해진 것:
- 언어는 TypeScript다. 수집 앱·서버·`packages/shared`가 TypeScript이고(ADR 0001 제안), 공유 타입을 그대로 가져다 써야 한다.
- 3D는 Three.js다. 팀원 시안이 Three.js를 쓰고 있다 (PRD Q9 후보).
- 웹은 로컬 서버가 정적 파일로 내려주고 사용자 브라우저에서 연다 (SPEC 3-3). 빌드 결과가 정적 파일이어야 한다.

남은 것은 **UI 프레임워크, 3D를 붙이는 방식, 상태 스토어, 빌드 도구**다.

### 판단 기준 (우선순위 순)

| # | 기준 | 왜 중요한가 |
| --- | --- | --- |
| 1 | **개발 A·B가 화면을 빨리 얹을 수 있는가** | 화면 4종 중 3종(패널·상세·탐사선)을 개발 A·B가 만든다. 사이드 패널, 모달, 폼, 목록이 대부분이다 |
| 2 | **3D 장면과 2D 화면이 같은 상태를 문제없이 나눠 쓰는가** | `flyToPlanet → openPanel`처럼 3D와 패널이 서로 부른다 (SPEC 2-5). 3D는 매 프레임 돌고, 패널은 상태가 바뀔 때만 다시 그려야 한다 |
| 3 | **3D 성능을 직접 다룰 수 있는가** | 별 2,000개 상한과 프레임 수 기준을 개발 C가 1주 차에 재야 한다 (POLICY 3-4, PRD 2장) |
| 4 | 배우는 비용이 작은가 | 일정이 짧다. 자료가 많은 쪽이 막히는 시간을 줄인다 |

### 환경 제약 (2026-11-11 확인)

개발 B의 윈도우 PC에서 **Windows Application Control 정책이 `@rollup/rollup-win32-x64-msvc`의 `.node` 네이티브 파일 로드를 막았다** (`ERR_DLOPEN_FAILED`). 그래서 `packages/shared` 테스트는 vitest 대신 Node 내장 `node:test`로 바꿨다. Vite도 빌드에 rollup을 쓰므로 같은 PC에서 막힐 수 있다. 대응 후보(직접 확인 필요): `@rollup/wasm-node`로 바꿔 쓰기(`overrides`), 회사·학교 PC의 정책 예외 요청, 해당 팀원은 다른 PC에서 빌드.

> 위 환경 제약은 #13으로 먼저 들어온 ADR 0002 초안(개발 B)에서 옮겼다. 1주 차 초에 팀원 PC 전부에서 `npm create vite` 템플릿이 dev·build 되는지, 막히면 `@rollup/wasm-node` overrides로 되는지 확인한다.

## 2. 고려한 대안들

**UI 프레임워크**

| 후보 | 장점 | 단점 / 채택하지 않은 이유 |
| :--- | :--- | :--- |
| **A. React** | 자료와 예제가 가장 많아 처음 쓰는 팀원도 막혔을 때 답을 찾기 쉽다. 패널·모달·폼 같은 2D 화면을 컴포넌트로 나눠 맡기 쉽다. 수집 앱 드롭존도 `.tsx`로 잡혀 있어(SPEC 5장) 팀 전체가 같은 방식을 쓴다 | 번들이 다른 후보보다 조금 크다. 로컬에서 여는 화면이라 영향은 작다 |
| B. 프레임워크 없이 TypeScript + DOM | 가장 가볍다. SPEC 5장의 웹 파일명(`.ts`)과 그대로 맞는다 | 패널·모달·목록의 다시 그리기와 이벤트를 직접 관리해야 한다. 개발 A·B의 화면 작업량이 크게 늘어 기준 1에 어긋난다. **기각** |
| C. Svelte | 코드가 짧고 가볍다 | 자료와 예제가 React보다 적어 막혔을 때 답을 찾기 어렵다 (기준 4). **기각** |

**3D를 붙이는 방식**

| 후보 | 장점 | 단점 / 채택하지 않은 이유 |
| :--- | :--- | :--- |
| **A. Three.js를 직접 쓰고 React 컴포넌트 하나(`UniverseCanvas`)로 감싼다** | 장면, 카메라 4상태(조망·비행·자동 비행·착륙), 렌더 루프를 직접 다룬다. 별을 `InstancedMesh` 하나로 그리는 식의 성능 조정이 쉽다 (기준 3). React가 매 프레임 관여하지 않는다 | 장면 객체의 생성·정리를 직접 해야 한다 |
| B. React Three Fiber (`@react-three/fiber`) | 3D도 JSX로 쓴다. 예제가 많다 | 비행 조작과 카메라 상태 머신은 어차피 직접 짜야 한다. 별 수천 개를 컴포넌트로 만들면 느려져서 결국 직접 Three.js로 내려간다. 추상화 층이 하나 늘어 성능 측정이 어렵다. **기각** |

**상태 스토어** (SPEC 2-5 `WebState`와 호출 계약 8종)

| 후보 | 장점 | 단점 / 채택하지 않은 이유 |
| :--- | :--- | :--- |
| **A. Zustand** | 아주 작다. React 밖(3D 렌더 루프)에서 `getState()`·`subscribe()`로 읽고 부를 수 있다 (기준 2). 컴포넌트는 필요한 값만 골라 구독해 쓸데없이 다시 그리지 않는다 | 의존성이 하나 는다 |
| B. React Context + `useReducer` | 의존성이 없다 | 3D 루프에서 상태를 읽으려면 따로 다리를 놓아야 한다. 값 하나가 바뀌어도 Context를 쓰는 화면이 다 다시 그려진다. **기각** |

**빌드 도구**: Vite. 정적 파일로 빌드되고, 개발 서버에서 `/api`를 로컬 서버로 넘길 수 있다. 다른 후보는 따로 비교하지 않았다.

## 3. 최종 결정 (제안) 및 이유

- 이 초안은 **React + Vite + TypeScript, 3D는 Three.js 직접 사용, 상태는 Zustand**를 제안한다.
- **제안 이유**:
  1. **기준 1**: 2D 화면이 대부분이고 그 대부분을 개발 A·B가 만든다. React는 자료가 가장 많고 컴포넌트 단위로 나눠 맡기 쉽다.
  2. **기준 2**: Zustand 스토어 하나가 `WebState`와 호출 계약 8종을 가진다. 패널은 훅으로, 3D는 `getState()`로 같은 스토어를 쓴다. `flyToPlanet`은 스토어가 훅 자리만 두고 3D 쪽이 등록한다.
  3. **기준 3**: 3D는 React 바깥의 Three.js 코드로 두고 `UniverseCanvas` 하나로 감싼다. 성능 측정과 조정을 개발 C가 직접 할 수 있다.
- **라우팅**: 경로가 4개(`#/`, `#/planet/:id`, `#/star/:id`, `#/probe`)뿐이라 라우터 라이브러리를 쓰지 않고 `hashchange`로 직접 처리한다.
- **버전** (작성일 기준 최신): React 19, Vite 8, Three.js 0.187, Zustand 5.

## 4. 예상되는 결과 및 영향

- **긍정적 영향**
  - 수집 앱 드롭존(React 가정)과 웹이 같은 방식을 쓴다. PO와 개발자가 서로 코드를 봐 줄 수 있다.
  - 3D 쪽 작업(개발 C)과 패널 쪽 작업(개발 A·B)이 스토어 계약만 맞추면 따로 진행된다.
- **주의할 점**
  - SPEC 5장의 웹 파일 중 화면 컴포넌트는 `.tsx`가 된다 (`home/`, `planet/`, `star/`, `probe/`, `ui/`). `main.ts`, `api/client.ts`, `state/store.ts`, `universe/*.ts`는 그대로 `.ts`다.
  - Three.js 객체(메시, 재질, 텍스처)는 React가 정리해 주지 않는다. `UniverseCanvas`가 사라질 때 `dispose()`를 직접 불러야 한다.
  - Vite 개발 서버는 로컬 서버와 출처가 다르다. 개발 중에는 Vite가 `/api`를 로컬 서버로 넘기거나(proxy) 목업을 쓴다. 서버의 Origin·Host 검사(POLICY 1-3)는 배포 빌드 기준으로 지키고, 개발용 예외는 개발 B와 정한다.
  - 배포 빌드(`web/dist`)를 로컬 서버가 어떻게 내려줄지는 개발 B와 정한다.
  - 1주 차 성능 측정(별 개수별 프레임 수)에서 기준에 못 미치면 3D 방식(2장 둘째 표)부터 다시 본다. UI 프레임워크 결정은 바꾸지 않는다.

## 5. 개발 B 검토 요청

1. React + Zustand 조합에 동의하나요? 패널·상세 화면을 만들 때 불편한 점이 있을까요?
2. 개발 중 `/api` 호출을 Vite proxy로 실제 서버에 넘길지, 서버가 나오기 전까지 목업(`mocks/api/`)을 쓸지 정하고 싶어요.
3. 배포 빌드(`web/dist`)를 서버가 정적 파일로 내려주는 방식에 동의하나요?

### 5-1. 개발 B 답변 (2026-11-11)

세 가지 모두 동의한다. 아래는 동의를 전제로 개발 B가 맡은 쪽(#4 서버, #5 화면)에서 정할 세부 사항이다. 위 결정 내용은 바꾸지 않는다.

1. **React + Zustand — 동의**
   - #5(행성 패널·별 상세)는 React 컴포넌트(`.tsx`)로 만들고 같은 스토어를 쓴다.
   - 스토어 계약(#2)에 함께 정할 것 — 수정 후 화면 갱신: 메모 수정·행성 옮기기는 서버가 돌려준 바뀐 별(`StarsResponse`, `packages/shared/types.ts`)을 스토어에 반영한다. 행성 합치기·삭제 뒤에는 행성별 개수가 바뀌므로 `GET /api/universe`를 다시 받는다.
2. **개발 중 `/api` — 동의 (목업과 proxy를 시기별로 둘 다 쓴다)**
   - #4 서버가 나오기 전: 웹이 `mocks/api/*.json`을 쓴다 (#2 완료 조건 "목업 API로 화면 전환이 동작").
   - 서버가 나온 뒤: Vite가 `/api`를 로컬 서버로 넘긴다(proxy, `changeOrigin: true`).
   - 서버 보안 검사(POLICY 1-3)의 개발용 예외: 서버를 `SPACELOG_DEV_ORIGIN=http://localhost:5173`으로 켤 때만 그 Origin을 허용한다. 변수가 없으면 지금처럼 거부한다 (ADR 0001 5장 서버 진입점 조건 3과 같음). 개발할 때는 서버를 `SPACELOG_TOKEN=dev`로 켜고 웹을 `#/?token=dev`로 연다.
3. **배포 빌드(`web/dist`)를 서버가 정적 파일로 내려줌 — 동의**
   - 웹과 API가 같은 출처(`127.0.0.1:{port}`)여야 Origin 검사를 예외 없이 지킬 수 있으므로 이 방식이 맞다.
   - #4에서 구현할 세부 사항:
     - 정적 파일은 토큰 없이 내려준다. 토큰은 페이지가 열린 뒤 읽히고, 정적 파일에는 기록 데이터가 없다. `/api/*`만 토큰을 검사한다.
     - `web/dist` 위치는 환경 변수 `SPACELOG_WEB_DIR`로 받는다. 수집 앱이 설치본 안의 경로를 넘긴다.
     - 해시 라우팅이라 서버는 `/`(index.html)만 주면 된다. 없는 경로는 404로 응답하고 index.html로 돌려주지 않는다.
     - `index.html`은 `Cache-Control: no-cache`. 해시가 붙은 빌드 파일은 오래 캐시한다.

상태를 "채택됨"으로 바꾸는 것은 개발 C가 이 답변을 확인한 뒤에 한다.
