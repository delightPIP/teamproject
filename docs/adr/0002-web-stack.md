# ADR 0002: 로컬 웹의 기술 스택 (PRD Q9)

- **상태**: 제안됨 (Proposed) — 개발 B·C가 1주 차 초에 확정
- **작성 일자**: 2026-11-11
- **결정 담당**: 개발 B, 개발 C (PRD 6장 공통 약속)
- **관련 문서**: [PRD 3장·6장·7장 Q9](../PRD.md), [SPEC 1-4~1-8, 2-5, 3-3~3-5, 5장](../SPEC.md), [ADR 0001](0001-collector-server-stack.md)

## 1. 배경 및 문제 상황

로컬 웹(우주 홈, 행성 패널, 별 상세, 탐사선)을 무엇으로 만들지 정해야 개발 C의 웹 뼈대(#2)와 `state/store.ts` 계약, 개발 A·B의 2D 화면 작업을 시작할 수 있다.

로컬 웹이 해야 하는 일:
- **3D 우주** (개발 C): 행성·별·궤도, 조망 시점 / 비행(WASD) / 자동 비행 / 착륙 카메라, 기간 안 별 최대 2,000개 (P 3-4 잠정)
- **2D 화면** (개발 A·B·C): 상단 바, 행성 목록, 사이드 패널, 대화상자, 토스트, 메모 편집, 미리보기 — 2D 요소가 화면 수로는 더 많다
- 해시 라우팅(`#/planet/:id`, `#/star/:id`, `#/probe`), 세션 토큰을 `sessionStorage`에 보관 (SPEC 3-3)
- 로컬 서버(ADR 0001)가 정적 파일로 내어준다 → 빌드 결과는 정적 파일이면 된다

### 판단 기준 (우선순위 순)

| # | 기준 | 왜 중요한가 |
| --- | --- | --- |
| 1 | **3D 작업량을 줄이는가** | 개발 C가 가장 무겁다 (PRD 8장 리스크) |
| 2 | **2D 화면을 세 사람이 나눠 만들기 쉬운가** | 개발 A·B·C가 같은 상태(`WebState`)와 공통 UI를 쓴다 (SPEC 2-5, 1-8) |
| 3 | 팀원의 3D 시안을 가져다 쓸 수 있는가 | 시안이 Three.js를 사용 (PRD Q9) |
| 4 | 팀 PC에서 빌드·테스트가 되는가 | 아래 "환경 제약" 참고 |
| 5 | 번들 크기·성능 | 로컬에서 열리므로 우선순위 낮음. 3D 프레임 수는 개발 C가 따로 잰다 |

### 환경 제약 (2026-11-11 확인)

개발 B의 윈도우 PC에서 **Windows Application Control 정책이 `@rollup/rollup-win32-x64-msvc`의 `.node` 네이티브 파일 로드를 막았다** (`ERR_DLOPEN_FAILED`). 그래서 `packages/shared` 테스트는 vitest 대신 Node 내장 `node:test`로 바꿨다. Vite도 빌드에 rollup을 쓰므로 같은 PC에서 막힐 수 있다. 대응 후보(직접 확인 필요): `@rollup/wasm-node`로 바꿔 쓰기(`overrides`), 회사·학교 PC의 정책 예외 요청, 해당 팀원은 다른 PC에서 빌드.

## 2. 고려한 대안들

| 후보 | 장점 | 단점 / 위험 |
| :--- | :--- | :--- |
| **A. Vite + TypeScript + Three.js (UI 프레임워크 없음)** | SPEC 5장 잠정안. 시안 코드를 거의 그대로 옮길 수 있다. 의존성이 가장 적다. 3D 루프를 직접 다뤄 성능 조정이 쉽다 | 패널·대화상자·목록 같은 2D 화면을 DOM으로 직접 그리고 갱신해야 한다. 세 사람이 각자 다른 방식으로 짤 위험이 있어 `ui/` 공통 규칙을 따로 정해야 한다 |
| **B. Vite + React + TypeScript + Three.js (React Three Fiber)** | 2D 화면이 컴포넌트 단위라 세 사람이 나눠 만들기 쉽다. `WebState`를 스토어(예: Zustand) 하나로 두고 3D와 2D가 같은 상태를 구독한다. 3D 장면도 컴포넌트로 쓴다 | 의존성과 배울 것이 늘어난다(React, R3F 생태계). 시안 코드를 R3F 방식으로 옮겨야 한다. 프레임마다 바뀌는 값(카메라)을 React 상태에 넣으면 느려지므로 규칙이 필요하다 |
| **C. Vite + React(2D) + Three.js 바닐라(3D 캔버스 하나)** | 2D는 React 컴포넌트로 나눠 만들고, 3D는 시안 코드를 그대로 쓴다. 둘 사이는 SPEC 2-5의 호출 계약(`flyToPlanet`, `openPanel` …)으로만 잇는다 | 3D와 React 사이 연결 코드(스토어 구독, 이벤트)를 개발 C가 직접 써야 한다 |
| D. 번들러 없이 ES 모듈 + import map | 빌드 도구가 없어 위 환경 제약을 피한다 | TypeScript를 쓰려면 결국 변환 단계가 필요하다. 의존성 관리가 불편하다. **기각** |

## 3. 최종 결정 (제안) 및 이유

- 이 초안은 **C. Vite + React(2D) + Three.js 바닐라(3D)** 를 제안한다. 개발 C가 시안을 R3F로 옮기는 편이 빠르다고 보면 B로 바꾼다.
- **제안 이유**:
  1. **기준 1·3**: 3D는 시안 코드를 그대로 쓴다. 개발 C가 새 3D 프레임워크를 배우지 않는다.
  2. **기준 2**: 2D 화면 수가 많고 세 사람이 나눠 만든다. 컴포넌트 단위(React)가 A보다 충돌이 적다. `packages/shared/types.ts`의 `WebState`를 스토어 하나로 두면 2-5 계약을 그대로 옮길 수 있다.
  3. SPEC 2-5의 호출 계약이 이미 3D와 2D 사이 경계를 정해 두었다. C는 그 경계를 코드 구조로 그대로 만든다.
- **바뀌는 조건**:
  - 개발 C가 시안 → R3F 이전을 하루 안에 할 수 있다고 판단 → B
  - 팀원 PC에서 Vite 빌드가 막히고 위 대응이 안 됨 → 해당 팀원 작업 방식 별도 논의 (D는 기각 유지)

## 4. 예상되는 결과 및 영향

- **긍정적 영향**
  - 웹 전체가 TypeScript로 `packages/shared`(타입·오류 코드·기간 유틸)를 그대로 가져다 쓴다.
  - 빌드 결과가 정적 파일이라 로컬 서버가 그대로 내어줄 수 있다 (ADR 0001과 무관).
- **주의할 점**
  - 프레임마다 바뀌는 값(카메라 위치, 비행 속도)은 React 상태에 넣지 않는다. 스토어에는 `camera` 모드처럼 화면이 바뀌는 값만 둔다.
  - 공통 UI(`ui/`)는 디자이너 2의 공통 요소가 나온 뒤 개발 C가 먼저 만들고 A·B가 쓴다 (#2).
  - 웹 테스트 도구는 위 환경 제약을 보고 정한다 (vitest는 rollup에 의존).
